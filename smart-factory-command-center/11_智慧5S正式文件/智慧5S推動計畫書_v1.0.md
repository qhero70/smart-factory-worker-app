## 二、計畫摘要

本計畫以化新精密既有智慧工廠架構為基礎，導入可安裝於手機、平板與電腦的智慧 5S PWA，串接既有 Google Apps Script、⭐智慧工廠主資料庫、唯一 LINE Bot 與 GitHub 版本管理，不建立第二套資料庫、第二個 LINE Bot 或重複入口。

推動策略採「示範區驗證、種子教官複製、分區展開、全廠標準化」四階段進行。第一階段聚焦 A9 簡單專線、1069 檢驗桌、1070 檢驗桌與紅牌暫存區，先建立可被全廠複製的照片基準、定位規則、巡檢清單、改善責任與紅牌處置節奏。

系統截至 2026 年 8 月 6 日已完成正式 API 接線、15 張 5S 分頁、PWA 離線外殼與正式寫入閉環；唯讀驗收 48／48 通過，正式新增與更新閉環 18／18 通過。現場推動的主要工作已由「開發系統」轉為「建立標準、完成實機驗收、培訓人員、穩定執行與數據複盤」。

> 推動閉環：現況盤點 → 基準建立 → 每日復原 → 行動巡檢 → 異常改善 → 主管驗證 → KPI 複盤 → 分區展開。

### 2.1 管理決策重點

- 先核准 A9 示範區與角色責任，再擴大到其他區域。
- 以現場照片與定位標示建立一致判斷，降低不同人員的主觀落差。
- 異常必須有原因、照片、責任人與期限；主管驗證後才能結案。
- 非必要品以紅牌及暫存區管理，不允許只搬移、不判定、不結案。
- KPI 先取得四週基準值，再以達成率與改善速度管理，不以單次大掃除作為成果。
- LINE 推播只送到已確認的 5S 正式群組；群組識別碼未確認前不得啟用排程。

## 三、推動背景與問題

### 3.1 現場管理痛點

- 文件、量檢具、治具、清潔工具、飲料容器與臨時物品缺乏一致的必要性判定及定位規則。
- 檢驗桌、專線與暫存區容易因人員、班別或追單壓力而恢復雜亂。
- 5S 執行常停留在活動照片，缺少異常責任、期限、驗證與結案紀錄。
- 紅牌物品可能只被移到其他位置，沒有處置類別、會辦、證據與結案狀態。
- 主管難以即時掌握哪些區域未巡檢、哪些改善逾期、哪些紅牌尚未處置。
- 紙本或聊天訊息無法形成可追溯資料，也難以計算趨勢、排名與改善成效。

### 3.2 推動必要性

智慧 5S 不只是整理現場，而是建立生產穩定、安全、品質與效率的共同基礎。透過統一的檢查項目、照片證據、改善閉環與數據看板，可把「誰認為乾淨」改成「依同一標準判定」，並讓跨班別、跨區域與主管層級使用同一份事實。

## 四、計畫目標

### 4.1 短期目標（核准後 1～6 週）

1. 完成 A9 四個示範區的責任人、平面範圍、定位標示及基準照片。
2. 完成正式人員登入、手機相機、離線補送、PWA 安裝與 LINE 群組推播實機驗收。
3. 建立每日自主管理、每週主管抽查與每月管理複盤節奏。
4. 所有異常、改善、紅牌與處置均由智慧 5S 平台留下完整軌跡。
5. 培養第一批種子教官，使示範區做法能複製到各組及其他產線。

### 4.2 中期目標（核准後 7～12 週）

1. 將示範區標準複製到同組其他區域，並完成差異調整。
2. 建立區域巡檢完成率、平均得分、異常密度、改善準時率與紅牌結案率。
3. 重大異常及逾期案件由唯一 LINE Bot 通知正確群組及責任主管。
4. 主管會議以平台數據取代人工彙整與口頭追問。

### 4.3 長期目標（12 週後）

1. 形成全廠一致的智慧 5S 管理辦法、SOP、稽核制度與教育訓練教材。
2. 將 5S 結果與品質、安全、交期、設備及改善提案進行關聯分析。
3. 讓 5S 成為班前、換線、交接、異常處理及現場主管巡視的固定工作方式。

## 六、推動原則

1. 必要性優先：先判定是否需要，再決定放在哪裡，不以增加櫃子取代整理。
2. 使用頻率分層：每日使用放在伸手可及位置；每週、每月及少用物品逐層外移；用不到物品進入紅牌流程。
3. 一物一位：每項保留物品須有名稱、位置、數量上限與責任人。
4. 目視可判定：合格與異常必須能從照片、標線、標籤與數量上限快速辨識。
5. 異常必閉環：低於滿分的項目須記錄原因與照片，並依嚴重度建立改善與通知。
6. 驗證後結案：改善人不能自行宣告完成；由主管或區域負責人確認證據後結案。
7. 數據只留一份：所有 5S 正式資料寫回⭐智慧工廠主資料庫，Git 保存程式與文件版本。
8. 現場可離線：訊號不佳時仍可開啟 PWA、暫存作業並在恢復網路後補送。

### 7.1 權限原則

- 現場人員：登入、巡檢、提交改善證據及查看本人／所屬區域案件。
- 區域負責人：管理所屬區域標準、執行抽查、追蹤改善及紅牌。
- 主管：驗證、駁回、結案、查看跨區域 KPI 與逾期案件。
- 系統管理員：維護主檔、參數、版本、觸發器及資料修復，不代替主管做現場判定。

## 八、系統架構與資料治理

### 8.1 單一正式架構

智慧 5S 採 PWA 為操作核心，經既有 GAS Web App 寫入⭐智慧工廠主資料庫；重大異常與紅牌進入 5S 通知紀錄，再由既有 NEXUS OS 唯一 LINE Bot 橋接發送。前端、GAS、文件與部署紀錄均由 GitHub 管理版本。

### 8.2 架構元件

| 元件 | 正式用途 | 管制原則 |
|---|---|---|
| 智慧 5S PWA | 登入、巡檢、改善、紅牌、設定與戰情 | 繁體中文、可安裝、Large Tap、可離線啟動 |
| Google Apps Script | API 路由、資料驗證、照片處理、統計與觸發器 | 沿用既有專案；更新資料列僅允許 5S 分頁 |
| ⭐智慧工廠主資料庫 | 人員、區域、巡檢、改善、紅牌、照片、通知、KPI | 唯一正式資料來源；表頭與狀態字典受控 |
| 既有唯一 LINE Bot | 重大異常、紅牌及逾期提醒 | 權杖不進 Git；收件群組確認後才啟用 |
| GitHub | 前端、GAS、文件、測試與部署紀錄 | 每次變更需有提交、驗收與回復依據 |

### 8.3 資料品質規則

- 人員只引用既有 01_人員主檔，不另建帳號名冊。
- 區域、檢查項目、嚴重度、狀態與處置類別使用受控主檔或下拉選單。
- 巡檢、改善、紅牌與處置皆使用唯一編號，禁止以列號作為業務主鍵。
- 所有更新須保留建立時間、更新時間、執行人與歷程。
- 驗收資料使用 SYSTEM-5S-TEST 及「智慧5S自動驗收」標記，與正式績效分離。
- 照片不得包含與 5S 判定無關的個人敏感內容；保存年限由管理辦法另訂。

## 九、作業流程

### 9.1 每日自主復原

1. 班前或交接時依基準照片確認通道、桌面、工具、文件與清潔用品。
2. 超出定量或不明物品先移入待判定位置，不直接塞入抽屜或其他區域。
3. 發現立即可排除的小問題，完成復原後仍於巡檢中記錄。
4. 無法當班排除或涉及安全、品質、跨部門的問題，建立改善單並指定責任與期限。

### 9.2 巡檢與異常

1. 人員以工號或姓名登入並選擇區域。
2. 依 5、3、1、0 分判定：5 分符合、3 分輕微偏差、1 分異常、0 分重大異常。
3. 低於 5 分須填寫原因與照片；系統建立改善單及改善歷程。
4. 重大異常寫入通知紀錄；LINE 收件設定完成後由唯一 Bot 發送。
5. 巡檢送出後不可直接改寫原始判定；後續處置走改善歷程。

### 9.3 改善與驗證

1. 責任人接受案件並將狀態由待改善轉為改善中。
2. 完成處置後拍攝改善後照片、填寫說明並送驗。
3. 主管或區域負責人檢查現場、證據與持續性。
4. 符合則結案；不符合則駁回，記錄原因並回到改善中。
5. 逾期案件列入主管戰情及週會追蹤，不以口頭承諾取代系統紀錄。

### 9.4 物品盤點與紅牌

1. 依每日、每週、每月、很少使用、用不到判定使用頻率。
2. 確認必要性、保留上限、責任部門及建議處置。
3. 非必要品自動建立紅牌與改善單，移至紅牌暫存區並標示期限。
4. 依移轉、退庫、報廢、回收或其他核准方式處置。
5. 具備證據、會辦確認及複查後，由授權人員結案。

| 巡檢完成率 | 已完成巡檢數／應巡檢數 | 巡檢主檔 | ≥95％ | 日／週 |
| 平均得分率 | 總得分／最高總分 | 巡檢主檔 | 連續改善，不低於核准基準 | 週／月 |
| 異常改善準時率 | 期限內結案件數／到期案件數 | 改善單 | ≥90％ | 週 |
| 逾期改善占比 | 逾期未結案件／未結案件 | 改善單 | ≤5％ | 日／週 |
| 紅牌準時處置率 | 期限內結案紅牌／到期紅牌 | 紅牌追蹤 | ≥90％ | 週／月 |
| 重複異常率 | 同區同項重複異常／全部異常 | 巡檢明細、改善單 | 月減 10％或低於核准基準 | 月 |
| 主管驗證時效 | 送驗至驗證的中位時間 | 改善歷程 | ≤2 個工作日 | 週 |
| 資料同步成功率 | 成功寫入且無重複／送出總數 | 通知及系統紀錄 | ≥99％ | 週 |
| 重大通知時效 | 建立通知至成功送出的時間 | 通知紀錄 | 群組啟用後 ≤10 分鐘 | 月 |

### 12.1 KPI 使用原則

- KPI 用於改善流程與資源，不以單一分數直接處罰個人。
- 驗收資料、作廢資料與系統測試帳號不得計入正式績效。
- 分數提升必須同時確認重複異常、逾期與紅牌是否下降，避免只追求表面得分。
- 指標定義、分母、排除條件與版本變更必須留在 KPI 手冊及系統參數中。

## 十三、風險與控制措施

| 風險 | 可能影響 | 預防措施 | 發生後處理 | 責任角色 |
|---|---|---|---|---|
| 標準不一致 | 同一現場不同人判定結果不同 | 基準照片、文字標準、交叉判定訓練 | 種子教官複判並修訂清單 | 推動主責人／種子教官 |
| 為拍照而整理 | 短期好看但無法維持 | 每日復原、定量、責任與重複異常分析 | 針對復發原因做防呆 | 區域主管 |
| 改善單大量逾期 | 系統變成待辦堆積 | 合理期限、責任人、每週主管檢視 | 升級主管並調整資源 | 區域主管 |
| 紅牌只搬不處置 | 暫存區變成永久倉庫 | 30 天期限、上限、處置類別與證據 | 暫停新增並召開處置會議 | 責任部門／主管 |
| 現場網路不穩 | 無法即時送出或照片失敗 | PWA 離線佇列、照片壓縮、同步提示 | 恢復網路後補送並查重 | 系統管理員 |
| LINE 誤發 | 通知送到錯誤既有群組 | 群組識別碼雙人確認，空白不發送 | 停用觸發器、修正對照並留下紀錄 | LINE 群組管理者 |
| 資料錯列或狀態不合法 | 改善與紅牌流程中斷 | 表頭對齊、5S 分頁限制、受控狀態字典 | 封存異常批次並修補後回歸測試 | 系統管理員 |
| 人員抗拒或不熟悉 | 巡檢流於形式、資料品質差 | 大按鈕、繁體中文、現場實作、種子教官 | 一對一輔導並簡化不必要欄位 | 推動主責人 |

## 十四、資源與費用原則

- LINE 官方帳號用量超過既有方案時，依實際訊息量另行評估。
